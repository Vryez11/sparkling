02 · Key Relationships

ERD에서 중요한 관계 3개

셀프 조인

💬 comments → comments

  • parent_comment_id가 같은 테이블의 id를 참조
  • 대댓글을 별도 테이블 없이 표현
  • 최상위 댓글은 NULL, 대댓글은 부모 댓글을 가리킴
한 테이블에 FK 2개

🤝 chat_requests → users

  • request_user_id / response_user_id 둘 다 users.id 참조
  • 같은 users를 역할이 다른 두 관점으로 참조 (보낸 사람 / 받은 사람)
  • 조회 시 users를 두 번 조인
N:M 해소

🏷️ posts ↔ hashtags

  • 게시글 하나에 태그 여러 개, 태그 하나에 게시글 여러 개 → N:M
  • 중간 테이블 post_hashtag로 1:N + N:1 두 개로 분해
  • UNIQUE(post_id, hashtag_id)로 중복 연결 방지
03 · Design Decision

좋아요/댓글/게시글을 이렇게 나눈 이유

게시글 좋아요

👍 posts에 카운트 컬럼? → 테이블 분리

  • 처음엔 posts.like_count로 바로 세는 것도 고려
  • 하지만 "누가" 눌렀는지 확인해야 하는 상황이 있음 — 중복 좋아요 방지, 좋아요 취소, 내가 누른 글 확인
  • 카운트만 저장하면 "누가"가 사라짐 → post_likes로 분리
  • 카운트는 COUNT(*)로 언제든 계산 가능
댓글 좋아요

💬 댓글도 같은 논리로 분리

  • 댓글에도 좋아요 기능이 필요
  • 같은 이유로 comments와 comment_likes를 분리
  • 대상만 다를 뿐 구조는 post_likes와 동일 (user + 대상 + UNIQUE)

→ 집계는 계산으로, "누가 했는가"는 행(row)으로 남긴다.
