# 인증 설계

## 비밀번호 저장

비밀번호는 평문이 아니라 해시로 저장한다. 서버는 사용자의 실제 비밀번호를 알 필요가 없고, "입력값의 해시가 저장된 해시와 같은가"만 확인하면 되기 때문이다. 
해시는 일방향 함수라서 DB가 유출되어도 해시값에서 비밀번호를 역산할 수 없다. 복호화가 가능한 암호화(encryption)를 쓰지 않는 이유도 같다.

## 알고리즘 선택: 왜 Argon2인가

비밀번호 해시 알고리즘은 일부러 느리게 설계된 것을 써야 한다. 로그인 한 번에 수십 ms가 걸려도 사용자는 체감하지 못하지만, 유출된 해시를 놓고 수십억 번 대입해야 하는 공격자에게는 치명적이기 때문이다. 
후보는 PBKDF2, BCrypt, Argon2 세 가지였다.

| | PBKDF2 | BCrypt | Argon2id |
|---|---|---|---|
| 방어 자원 | CPU 시간 | CPU 시간 + 4KB 고정 메모리 | CPU 시간 + **조절 가능한 메모리** |
| GPU/ASIC 내성 | 약함 | 중간 | 강함 |
| 방어 강도 조절 | 반복 횟수 | cost factor | 메모리(m), 반복(t), 병렬(p) |

`판단 기준`: 공격자는 서버와 같은 하드웨어를 쓰지 않는다. GPU는 수천 개 코어로 해시 계산을 병렬화하므로, CPU 시간만으로 방어하는 알고리즘은 단위 비용당 공격 시도 횟수에서 계속 밀린다.

- **PBKDF2**: 메모리를 거의 쓰지 않아 GPU 병렬화에 가장 취약하다. 표준화(FIPS)가 필요한 환경이 아니면 선택할 이유가 없다.
- **BCrypt**: 내부적으로 4KB 테이블을 계속 읽고 써서 GPU 병렬화를 어느 정도 방해하고, 지금도 충분히 안전하다. 다만 이 4KB가 설계에 고정되어 있어 공격 하드웨어가 발전해도 방어 측에서 키울 수 없다.
- **Argon2id**: 메모리 사용량이 파라미터(m)라서 하드웨어 발전에 맞춰 방어 강도를 메모리 축으로도 올릴 수 있다. 해시 하나를 계산하는 데 수십 MB를 강제하면, GPU는 코어 수가 아니라 메모리 총량으로 병렬 개수가 제한되고 ASIC도 메모리가 실리콘 면적을 차지해 비용 절감 폭이 작아진다. Password Hashing Competition(2015) 우승 알고리즘이고, RFC 9106으로 표준화되었으며, OWASP가 1순위로 권장한다.

신규 시스템이므로 마이그레이션 부담 없이 **Argon2id**를 선택했다.

Argon2의 세 변형 중에서는 **Argon2id**를 쓴다. 메모리 참조 위치가 비밀값에 의존하는 Argon2d는 시간-메모리 트레이드오프(TMTO) 공격에 강하지만 부채널(캐시 타이밍)에 약하고, 데이터 독립적인 Argon2i는 그 반대다. Argon2id는 첫 순회 절반을 i 방식, 나머지를 d 방식으로 처리하는 하이브리드로, RFC 9106의 권장 기본값이다.

## 적용

Spring Security의 `Argon2PasswordEncoder`를 사용한다.

```java
@Bean
public PasswordEncoder passwordEncoder() {
    // saltLength=16B, hashLength=32B, p=1, m=19456KiB(19MiB), t=2
    return new Argon2PasswordEncoder(16, 32, 1, 19456, 2);
}
```

파라미터는 OWASP 최소 기준(m=19MiB, t=2, p=1)을 따랐다. 튜닝 원칙은 "로그인 한 번에 0.5~1초를 넘지 않는 한도에서 m을 최대한 키운다"이며, m은 동시 로그인 요청 수만큼 서버 RAM을 실제로 소모하므로 트래픽을 감안해 정한다.

서비스 코드는 `PasswordEncoder` 인터페이스에만 의존한다. 저장 시 `encode()`, 로그인 검증 시 `matches(평문, 저장된해시)`를 쓴다. 
`encode()`는 호출마다 새 랜덤 솔트를 생성해 같은 비밀번호라도 매번 다른 결과가 나오므로, 검증할 때 `encode()`를 다시 호출해 문자열 비교를 하면 안 된다.

## 저장 형식 — 파라미터와 솔트가 보여도 되는 이유

DB에는 아래 형태의 문자열 하나가 저장된다.

```
$argon2id$v=19$m=19456,t=2,p=1$c29tZXJhbmRvbXNhbHQhIQ$dGhpc2lzbm90YXJlYWxoYXNo...
```

- `$argon2id`: argon2 종류
- `v=19`: 버전
- `m=19456, t=2, p=1`: 파라미터
- `$c29tZXHhbm~` (16비트) : 솔트
- `$dGhpc2l~` (32비트) : 해시값

변형, 버전, 파라미터, 솔트가 전부 평문으로 노출되어 있는데, 이는 의도된 설계다.

`솔트를 저장하는 이유`: 검증할 때 가입 시점과 **같은 솔트**로 다시 해시해야 비교가 가능하다. 솔트는 애초에 저장할 수밖에 없는 값이고, 별도 컬럼 대신 해시 문자열 안에 포함하는 방식을 쓴다.

`솔트가 공개되어도 안전한 이유`: 솔트의 방어 목표는 비밀 유지가 아니라 **사전 계산 무력화**다. 솔트가 없으면 공격자는 "흔한 비밀번호 → 해시" 대응표(레인보우 테이블)를 미리 만들어 유출된 해시를 조회하는 것으로 끝나고, 같은 비밀번호를 쓰는 사용자들이 같은 해시를 갖게 되어 한 명이 뚫리면 전원이 뚫린다. 사용자마다 다른 랜덤 솔트를 섞으면 미리 계산해 둔 표가 무용지물이 되고, 같은 비밀번호도 서로 다른 해시가 된다. 공격자가 솔트를 알아도 얻는 것은 "그 한 명을 대상으로 처음부터 brute-force할 권리"뿐이며, 그 brute-force는 후보 하나당 19MiB 메모리 연산을 요구하도록 Argon2가 막고 있다.

## 인증 상태 관리: 왜 JWT인가

HTTP는 무상태(stateless)다. 로그인에 성공해도 서버는 다음 요청에서 그 사실을 기억하지 못하므로, "로그인했음"을 이후 요청마다 증명할 수단이 필요하다. 후보는 두 가지였다.

- **세션**: 서버가 저장소에 "세션ID → 사용자"를 기록하고, 클라이언트는 세션ID만 쿠키로 들고 다닌다. 상태가 **서버에** 있다.
- **JWT**: 서버가 "이 사람은 N번 사용자, 언제까지 유효"라고 적고 **비밀키로 서명한 토큰**을 클라이언트에게 통째로 준다. 서버는 아무것도 저장하지 않고 요청마다 서명만 검증한다. 상태가 **클라이언트에** 있다.

| | 세션 | JWT |
|---|---|---|
| 상태 저장 위치 | 서버 (메모리/Redis) | **클라이언트 (토큰 자체)** |
| 요청 검증 방법 | 저장소에서 세션ID 조회 | 서명 검증 (연산만, 조회 없음) |
| 서버 수평 확장 | 세션 공유 저장소 필요 | 비밀키만 공유하면 됨 |
| 강제 무효화 (즉시 로그아웃/차단) | 서버에서 삭제하면 즉시 | **만료 전까지 불가능** |
| 주 전달 수단 | 쿠키 (브라우저 중심) | `Authorization: Bearer` 헤더 |

`판단 기준`: 이 서버는 화면을 렌더링하지 않는 순수 API 서버고, 클라이언트가 분리되어 있다. 쿠키-세션은 브라우저에 묶인 메커니즘이라 웹 외 클라이언트와 궁합이 나쁘고, 서버가 늘어나면 세션 공유 인프라(Redis 등)가 추가로 필요해진다. JWT는 별도 저장소 없이 서버를 무상태로 유지할 수 있어 API 서버 구조와 맞고, Spring Security 설정의 `SessionCreationPolicy.STATELESS`와도 일관된다.

### 구조 — 서명이 신뢰의 근거

JWT는 `header.payload.signature` 세 덩어리를 각각 Base64URL로 인코딩해 점으로 이은 문자열이다. Header는 서명 알고리즘(HS256), Payload는 클레임(`sub`=userId, `iat`=발급 시각, `exp`=만료 시각), Signature는 앞 두 덩어리를 서버만 아는 비밀키로 HMAC 서명한 값이다.

공격자가 payload의 `sub`를 바꿔치기하면 내용과 서명이 불일치해 검증 단계에서 거부된다. 내용에 맞는 새 서명을 만들려면 비밀키가 필요한데, 그것은 서버 밖으로 나가지 않는다.

### payload가 보여도 되는 이유

Base64URL은 인코딩이지 암호화가 아니어서 payload는 누구나 디코딩해 읽을 수 있다. 서명이 보장하는 것은 기밀성이 아니라 **무결성(위조 불가)**이다. 따라서 payload에는 비밀번호·개인정보를 넣지 않고 userId만 넣는다. Argon2 저장 형식에서 파라미터와 솔트가 공개되어도 안전한 것과 같은 원리로, 구조는 전부 공개하고 보안은 비밀키 하나에 집중하는 설계다. 뒤집어 말하면 **비밀키가 유출되는 순간 누구나 유효한 토큰을 위조할 수 있으므로**, 키는 git에 커밋하지 않고 `.env`로 분리해 주입한다.

### 선택의 대가와 완화

JWT의 약점은 장점과 같은 지점에서 나온다. 서버에 기록이 없으므로 **발급된 토큰을 만료 전에 무효화할 수 없다.** 탈취당해도 만료 시각까지는 유효하다는 뜻이다. 완화책은 만료를 짧게 잡는 것이며, 액세스 토큰 수명을 30분으로 설정했다. 이후 리프레시 토큰을 도입하면 "짧은 액세스 토큰 + 서버가 관리(폐기 가능)하는 리프레시 토큰" 구조로 무상태의 이점과 무효화 능력을 절충할 수 있다.

### 무효화 전략 — 무엇을 저장할 것인가

"무효화할 수 없다"를 뒤집으면 "무효화하려면 서버에 상태가 필요하다"가 된다. 즉 무효화는 저장 여부의 문제가 아니라, **무상태의 이점을 얼마나 포기하고 무효화 능력을 얼마나 살 것인가**의 스펙트럼이며, 무엇을 저장하느냐에 따라 세 단계로 나뉜다.

| | 저장 대상 | 조회 시점 | 무효화 | 대가 |
|---|---|---|---|---|
| 화이트리스트 | 발급한 **모든** 액세스 토큰 | 매 요청 | 즉시 | 무상태 이점 전부 상실 |
| 블랙리스트 | **폐기된** 토큰만 | 매 요청 (작은 목록) | 즉시 | 요청당 조회 부활 (경량) |
| 리프레시 토큰 저장 | 리프레시 토큰만 | 갱신 시에만 | 다음 갱신부터 | 즉시 차단은 불가 |

- **화이트리스트**: 요청마다 "이 토큰이 DB에 있는가"를 조회한다. 무효화는 완벽하지만 "요청마다 서버 저장소 조회"가 부활하므로, 토큰 포맷만 JWT일 뿐 의미론은 세션이다. 이럴 것이라면 처음부터 세션이 더 단순하다.
- **블랙리스트**: 로그아웃·탈취 신고된 토큰**만** 저장하고, 각 항목에 토큰의 남은 수명만큼 TTL을 걸어 자동 소멸시킨다(Redis가 적합). 저장 대상이 전체가 아니라 예외뿐이라 가볍고, 즉시 무효화가 필수 요구사항일 때의 현실적 절충이다.
- **리프레시 토큰 저장**: 액세스 토큰(30분, 무상태)은 저장하지 않고, 장수명 리프레시 토큰만 DB에 저장한다. 탈취 의심 시 리프레시 토큰을 삭제하면 다음 갱신부터 차단되고, 이미 발급된 액세스 토큰의 피해는 최대 30분으로 상한이 잡힌다.

`판단 기준`: 매 요청 검증은 수백~수천 배 더 빈번하고, 갱신·폐기는 드물다. **자주 일어나는 일은 무상태로 처리하고, 드물게 일어나는 일에만 상태를 쓴다** — 리프레시 토큰 저장 방식이 표준 구조가 된 이유이고, 요청 경로에서 조회를 없애려고 JWT를 선택한 이 프로젝트의 결정과도 일관된다. 현재는 순수 무상태(30분 만료)로 시작하며, 리프레시 토큰 도입 시 이 구조로 확장한다.
