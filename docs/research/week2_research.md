### 1. 사용자 시나리오와 기능 목록의 차이

#### 조사 내용

> **사용자 시나리오**
>
> 사용자가 서비스를 이용할 때 예상되는 행동의 흐름을 시간 순서대로 서술한 것.
> 주어는 **사용자**이며, 한 편의 이야기처럼 읽힌다.

> **기능 목록**
>
> 서비스가 제공해야 하는 개별 기능을 나열한 것.
> 주어는 **서비스(시스템)** 이며, 각 항목은 순서 없이 독립적으로 존재하고
> 항목 하나가 곧 개발 작업 하나(구현 단위)가 된다.

```text
같은 회원가입을 다뤄도 서술 단위가 다르다.

시나리오 한 줄:
    "사용자는 이메일과 비밀번호를 입력하고 가입하기 버튼을 누른다"

기능 목록으로 쪼개면:
    ① 이메일/비밀번호 입력 폼 제공
    ② 이메일 형식 검증
    ③ 이메일 중복 확인
    ④ 비밀번호 암호화 저장
    ⑤ 가입 처리 및 완료 응답
```

#### 왜 시나리오를 먼저 쓰는가

기능 목록은 기능 **사이의 연결**을 말해주지 않는다. 기능이 전부 구현되어도
흐름이 끊긴 서비스가 나올 수 있다.

```text
1. 전이 누락   → 가입 버튼을 누른 "다음" 사용자가 어디로 가는지는
                기능 목록 어디에도 없다.
2. 예외 흐름 누락 → 이메일 중복이면? 형식 오류면? 실패 시 흐름은
                시나리오에서 "실패하면?"을 물어야 드러난다.
3. 근거 없는 기능 → 시나리오에서 도출하면 모든 기능에
                "어느 흐름의 어느 단계인가"라는 존재 이유가 생긴다.
```

예외 시나리오는 **구체적 원인 + 사용자의 인지 + 실패 후 상태** 3요소를 담는다.

> "사용자가 이미 가입된 이메일로 가입을 시도하면, '이미 가입된 이메일입니다'
> 문구가 표시되고, 입력한 값이 유지된 채 입력 폼에 머무른다."

#### 아직 확신 없는 점 (막혔던 부분)

- 기능 목록만으로 개발했을 때 생기는 구체적 문제를 바로 답하지 못했다.
  → 노션 정리: [사용자 시나리오와 기능 목록](https://app.notion.com/p/3998e70ba5ff81ae9fe2fd0a2c915763)

### 2. REST API 기본 원칙

#### 조사 내용

> **REST (REpresentational State Transfer)**
>
> 자원(Resource)의 상태(State)를 표현(Representation)에 담아 주고받는 아키텍처 스타일.
> 특정 기술이 아니라 HTTP를 잘 활용하기 위한 **제약 조건들의 집합**이며,
> "RESTful하다" = 이 제약 조건을 잘 지켜 설계했다는 의미다.

```text
실무 설계 규칙 (균일한 인터페이스의 구체화)

1. 자원은 URI로, 명사로        →  /posts, /posts/3
2. 행위는 HTTP 메서드로        →  GET(조회) POST(생성) PUT(전체 교체)
                                  PATCH(부분 수정) DELETE(삭제)
3. 결과는 상태코드로            →  201 생성, 400 잘못된 요청, 404 없음
4. 무상태(Stateless)           →  서버는 이전 요청을 기억하지 않는다
                                  → 매 요청에 필요한 정보(토큰 등)를 다 담는다
                                  → 어느 서버가 받아도 처리 가능 = 수평 확장 용이
```

> **멱등성(Idempotent)**
>
> 여러 번 호출해도 **서버 상태**가 한 번 호출했을 때와 같은 성질.
> GET·PUT·DELETE는 멱등, **POST만 멱등이 아니다** (호출마다 새 자원 생성).
> 네트워크 오류 시 재시도해도 안전한지 판단하는 근거가 된다.

#### 아직 확신 없는 점 (막혔던 부분)

- REST의 약자와 "RESTful"의 의미를 답하지 못했다.
  → 노션 정리: [REST API 기본 원칙](https://app.notion.com/p/3998e70ba5ff81dabf1bcc9b4d6a159d)
- DELETE의 멱등성 판단에서 두 번째 호출의 404 응답에 끌려 틀렸다.
  **멱등성의 기준은 응답이 아니라 서버 상태다.**
  → 노션 보강: [4. HTTP 메서드](https://app.notion.com/p/3748e70ba5ff8122805cc499707ce358)

### 3. JWT (REST 무상태에서 이어진 심화)

#### 조사 내용

> **JWT (JSON Web Token)**
>
> 인증 정보를 JSON으로 담고 서명해서 주고받는 토큰.
> 서버가 로그인 상태를 저장하는 대신(세션) 클라이언트가 서명된 토큰을 들고 다니고,
> 서버는 매 요청 서명만 검증하므로 **무상태**가 유지된다.

```text
구조: Header.Payload.Signature

Header    : 서명 알고리즘 (예: HS256)
Payload   : 클레임 — 사용자 ID, 만료 시간(exp) 등
Signature : Header + Payload를 서버만 아는 비밀 키로 서명한 값
            → 위조를 막는 부분. Payload를 바꿔치기하면 서명이 안 맞는다.

주의: Header/Payload는 암호화가 아니라 Base64 인코딩일 뿐 (누구나 열람 가능).
     JWT가 보장하는 것은 무결성이지 기밀성이 아니다.
     → Payload에 민감 정보를 넣으면 안 된다.
```

```text
로그아웃·토큰 무효화 문제 (무상태의 대가)

서버에 지울 것이 없으므로 발급된 토큰은 만료 전까지 유효하다.

대응: 1. 클라이언트에서 삭제      → 탈취된 토큰은 못 막음
     2. 짧은 Access Token
        + 서버 저장 Refresh Token → 실무 표준. 로그아웃 시 RT 폐기
     3. 블랙리스트(Redis)         → 즉시 무효화되지만 매 요청 조회 비용

핵심: 2, 3 모두 서버에 상태를 다시 들여오는 것.
     무상태의 확장성과 즉시 무효화 능력은 트레이드오프 관계다.
     단, 일반 요청은 여전히 서명 검증만으로 처리(저장소 조회 0회)되고
     서버가 저장소를 보는 건 재발급 순간뿐이라 확장성 이점은 대부분 유지된다.
```

#### 아직 확신 없는 점 (막혔던 부분)

- JWT의 세 부분 구조를 답하지 못했다.
- 로그아웃/토큰 무효화 처리 방법을 답하지 못했다.
  → 노션 정리: [JWT (JSON Web Token)](https://app.notion.com/p/3998e70ba5ff811a95d3ef53fd0af986)
  → 두 개나 막힌 주제라 다음 세션에서 복습 필요

### 4. 공개 API와 인증 API를 나누는 기준

#### 기준

> **서버가 요청자를 식별해야만 올바른 응답을 만들 수 있는가**
> (+ 서비스 정책상 회원 전용인가)

```text
회원가입/로그인      → 공개 (인증을 받으러 오는 API. 막으면 닭과 달걀 문제)
게시글 작성          → 인증 (작성자를 기록해야 함)
내 정보 조회         → 인증 ('내'가 누군지 알아야 함)
게시글 목록 조회     → 자원의 성격에 따라 다르다:
                       모두에게 같은 게시판 목록이면 공개,
                       팔로잉 기반 개인화 피드면 인증
```

> **인증 vs 인가**
>
> 인증(Authentication)은 "너 누구야?"(신원 확인), 인가(Authorization)는
> "너 그거 할 권한 있어?"(권한 확인).
> 인증 실패 → **401 Unauthorized**, 인가 실패 → **403 Forbidden**
> (이름이 뒤바뀐 것처럼 헷갈리는 게 함정 — Unauthorized가 인증 쪽이다)

#### 내가 고른 방식 (프로젝트 적용)

SecurityConfig의 `authorizeHttpRequests`에서 `requestMatchers()`로 URL 패턴을 지정하고
`permitAll()`(공개) / `authenticated()`(인증)를 붙인다.

```java
.authorizeHttpRequests(auth -> auth
        .requestMatchers("/auth/login", "/members").permitAll()
        .requestMatchers(HttpMethod.GET, "/posts/**").permitAll()
        .anyRequest().authenticated()   // 나머지는 전부 잠근다
);
```

#### 이유

- **공개를 명시하고 나머지는 전부 잠그는** 구조가 안전한 기본값이다.
  새 API를 추가할 때 깜빡해도 공개되는 보안 사고를 막는다.
- 규칙은 위에서부터 순서대로 매칭되므로 구체적 패턴을 먼저, `anyRequest`를 마지막에 쓴다.
- 소유자 기반 인가("자기 글만 삭제")는 DB 조회가 필요하므로 SecurityConfig가 아닌
  **서비스 계층**에서 처리한다. URL 패턴만 아는 SecurityConfig에서는 판단할 수 없다.

#### 아직 확신 없는 점 (막혔던 부분)

- SecurityConfig에서 공개/인증을 나누는 구체적인 메서드를 답하지 못했다.
  → 노션 정리: [공개 API와 인증 API 구분 (Spring Security 설정)](https://app.notion.com/p/3998e70ba5ff817fa49cc06572b3fd09)
- 현재 프로젝트는 `anyRequest().permitAll()` 상태 — JWT 도입 시 위 형태로 변경 필요
