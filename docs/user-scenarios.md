# 유스케이스 시나리오

## 1. 목표: 사용자는 게시글 작성 후 등록을 통해 게시글 확인이 가능하다.

> **사전조건**: 로그인 상태
>
> ### 성공 시나리오
>
> 1. 사용자는 게시글을 작성한다.
> 2. 서버는 게시글, 게시글 작성 시간을 저장한다.
> 3. 서버는 게시글 저장 완료되었다는 응답을 준다.
> 4. 사용자는 자신의 게시글 목록에서 작성한 게시글 확인이 가능하다.
>
> ### 확장 시나리오
>
> 2. 서버에 게시글이 저장되지 않은 경우
>    1. 사용자에게는 완료하지 못했다는 alert를 띄운다.
>    2. 작성하던 내용을 유지한 채, 작성 화면에서 다시 등록을 시도할 수 있게 한다.

## 2. 목표: 사용자는 댓글 작성과 좋아요(게시글, 댓글)가 가능하다.

> **사전조건**: 로그인 상태
>
> ### 성공 시나리오
>
> 1. 사용자는 댓글을 작성한다.
> 2. 서버는 게시글에 매핑해서 댓글을 저장한다.
> 3. 사용자는 댓글에 대댓글을 작성할 수 있다(부모 댓글 지정). 서버는 depth 확인 후 부모 댓글에 매핑해 저장한다.
> 4. 사용자는 게시글 또는 댓글에 좋아요를 누를 수 있다.
> 5. 서버에서는 좋아요 개수가 증가하고, 증가한 좋아요 개수를 응답한다.
> 6. 사용자는 이를 통해 좋아요 개수 확인이 가능하다.
> 7. 사용자는 누른 좋아요를 취소할 수 있다. 서버는 개수를 감소시키고, 감소한 개수를 응답한다.
>
> ### 확장 시나리오
>
> 3. 대댓글 스레드를 한 번 더 열려고 하는 경우
>     1. 서버에서는 depth 체크를 통해, 스레드 depth를 확인한다.
>     2. 사용자에게 스레드 생성이 불가능하다는 alert를 띄운다.
>
> ### 제약사항
>
> - 대댓글 스레드는 한 번(depth 1)까지만 가능하다.
> - 좋아요는 한 사용자가 게시글/댓글 하나에 한 번만 가능하다. 이미 누른 상태의 등록, 누르지 않은 상태의 취소는 오류로 응답한다 — 클라이언트가 조회 응답의 상태를 보고 올바른 요청을 보낸다는 전제.

## 3. 목표: 사용자는 검색을 통해 게시글, 사용자 검색이 가능하다.

> **사전조건**: 없음 (검색은 비로그인도 가능). 단, 찾은 게시글에 댓글을 달려면 로그인 상태여야 한다.
>
> ### 성공 시나리오
>
> 1. 사용자는 검색 대상을 선택해 검색을 요청한다 — 게시글(제목, 내용, 해시태그 중 카테고리 선택) 또는 사용자(닉네임).
> 2. 게시글 검색이면, 서버는 선택한 카테고리로 검색해 찾은 게시글 목록을 반환한다.
> 3. 사용자 검색이면, 서버는 닉네임으로 검색해 찾은 사용자 프로필 목록을 반환한다.
> 4. 사용자는 찾은 게시글에 댓글을 달 수 있고, 찾은 사용자 프로필에서 1:1 채팅으로 진입할 수 있다.
>
> ### 확장 시나리오
>
> 2. 검색 결과가 없는 경우
>     1. 서버에서 찾은 게시글/사용자가 없다.
>     2. alert를 띄우지 않고, 사용자에게 빈 목록을 보여준다.

## 4. 목표: 사용자는 게시글 작성 시 해시태그 작성이 가능하다.

> **사전조건**: 로그인 상태
>
> ### 성공 시나리오
>
> 1. 사용자는 게시글 작성 시 내용 안에 `#` 을 이용해 해시태그 작성이 가능하다.
> 2. 서버는 게시글 저장 시 내용에서 해시태그를 파싱해 게시글과 매핑하여 저장한다.
> 3. 게시글을 읽을 때, 해시태그는 볼드체로 보인다.
> 4. 사용자는 해시태그 검색 카테고리를 통해 해당 해시태그가 매핑된 게시글 확인이 가능하다.
>
> ### 제약사항
>
> - 해시태그 파싱은 클라이언트가 아니라 **서버**가 담당한다. 클라이언트 파싱 결과는 신뢰할 수 없고, 해시태그를 실제로 사용(저장·검색)하는 쪽이 서버이기 때문이다.
> - 해시태그 검색은 게시글 제목/내용 검색과 분리된 별도 검색 카테고리로 제공한다.

## 5. 목표: 사용자는 게시글 작성자와 1:1 채팅이 가능하다.

> **사전조건**: 로그인 상태
>
> ### 성공 시나리오
> 
> 1. 사용자는 게시글의 상대방 프로필 또는 사용자 검색 결과의 프로필을 눌러, 1:1 채팅을 클릭한다.
> 2. 서버는 상대방의 온라인 상태를 확인한다. 온라인 상태는 WebSocket 연결 여부로 판단한다.
> 3. 서버는 상대방의 연결된 모든 디바이스에 채팅 요청 메시지를 푸시하고, 최초로 연결한 디바이스와 채팅을 연결한다.
> 4. 채팅방이 생성되고, 사용자와 상대방이 채팅이 가능하다.
> 5. 채팅방 나가기를 클릭을 통해 채팅방을 나갈 수 있다.
> 
> ### 확장 시나리오
> 
> 2. 상대방이 오프라인인 경우
>    1. 오프라인 상대와는 채팅방 연결이 되지 않으며, 사용자에게 상대방이 오프라인이라고 안내한다.
>    2. 이 후, 상대방이 온라인이 되면 채팅 요청이 있었음을 알리고 채팅방 초대하기가 활성화 된다.
>    3. 상대방이 채팅방 초대를 눌렀을 때, 사용자에게 연결을 시도한다.
>    4. 사용자가 연결 가능하면 채팅방이 다시 생성되고 사용자와 상대방이 채팅이 가능하다.
> 
> 3. 채팅 연결 요청 후 상대방의 수락이 없는 경우
>    1. 연결 요청 후 30초 안에 상대방이 수락하지 않으면, 타임아웃으로 연결 시도를 완전히 종료한다.
> 
> ### 제약사항
> 
> - 채팅 **메시지 내용**은 서버에 저장(기록)되지 않는다. 온라인 상태 기반의 실시간 중계만 한다. 단, 오프라인 상대에게 전달할 **대기 중인 채팅 요청 상태**는 상대가 온라인이 될 때까지 저장한다.
> - 채팅 세션은 유저 단위가 아니라 **디바이스 단위**로 관리한다.
> - 채팅 구조상 WebSocket이 필수이므로, 온라인 상태 확인도 별도 폴링 없이 WebSocket 연결 여부로 판단한다.

## 6. 목표: 사용자는 자신이 작성한 게시글을 수정·삭제하고, 자신이 작성한 댓글을 삭제할 수 있다.

> **사전조건**: 로그인 상태
>
> ### 성공 시나리오
>
> 1. 사용자는 자신이 작성한 게시글에서 수정 또는 삭제를 선택한다.
> 2. 서버는 요청자가 해당 게시글의 작성자 본인인지 확인한다.
> 3. 본인이 맞으면 서버는 수정/삭제를 반영하고 완료 응답을 준다.
> 4. 댓글도 같은 방식으로, 서버가 작성자 본인 확인 후 삭제를 반영한다.
>
> ### 확장 시나리오
>
> 2. 요청자가 작성자 본인이 아닌 경우
>    1. 서버는 권한 없음(403 Forbidden)으로 요청을 거절한다.
>    2. 사용자에게 권한이 없다는 안내를 띄운다.
