# 페이지네이션 설계

`GET /posts`가 살아 있는 게시글 전체를 한 번에 반환하고 있다. 게시글이 쌓일수록 응답 크기와 조회 시간이 같이 늘어나는 구조라 페이지네이션을 붙이기로 했고, 설계하면서 정한 것들과 이유를 남긴다.

범위는 게시글 목록만이다. 댓글 목록(`GET /posts/{postId}/comments`)도 전체 반환이긴 한데, 규약을 여기서 한 번 정해두면 나중에 그대로 가져다 쓰면 되므로 이번에는 손대지 않는다.

## 1. offset 방식으로 간다

`?page=0&size=10` 형태. Spring Data의 `Pageable`/`Page`가 그대로 지원해서 구현이 단순하고, 페이지 번호 UI를 만들 수 있다.

offset의 약점은 알고 시작한다. 뒤 페이지로 갈수록 앞의 행을 읽고 버려서 느려지는 것, 그리고 페이지를 넘기는 사이 새 글이 등록되면 중복이나 누락이 생기는 것. 전자는 수십만 건은 쌓여야 체감되는 문제고, 후자는 게시판 특성상 치명적이지 않다고 보고 감수한다.

cursor(keyset) 방식도 검토했다. `WHERE (created_at, id) < (마지막 값) ... LIMIT n` 식으로 조회해서 페이지 깊이와 무관하게 성능이 일정하고 중복·누락도 없다. 대신 페이지 번호로 점프할 수 없고, Spring Data가 자동으로 지원하지 않아 직접 구현해야 한다. 무한 스크롤로 UI를 바꾸거나 offset 성능 문제가 실제로 측정되면 그때 넘어간다.

## 2. 요청 파라미터

| 파라미터 | 타입 | 기본값 | 설명 |
|---|---|---|---|
| `page` | int | `0` | 페이지 번호, 0부터 시작 |
| `size` | int | `10` | 페이지당 게시글 수, 최대 50 |

- `page`는 0부터 시작한다. `Pageable` 기본과 맞추면 변환 로직이 필요 없다. 1-base로 노출하면 경계마다 ±1 변환이 들어가는데, 그 변환이 빠진 곳에서 off-by-one이 나기 쉽다. 0-base라는 건 api-spec에 명시한다.
- `size` 상한 50은 `?size=100000` 같은 요청으로 사실상 전체 조회가 되는 걸 막기 위한 것.
- 잘못된 값은 400 대신 보정한다. `page < 0` → 0, `size < 1` → 10, `size > 50` → 50. 목록 조회는 값이 이상해도 그럴듯한 목록을 주는 편이 낫고, 지금은 예외 처리 체계(`@RestControllerAdvice`) 미도입이라 400을 제대로 내릴 수단도 없다. 예외 처리 체계가 들어오면 재검토.

## 3. 응답 구조 — 전체 개수를 포함한다

기존 `{"posts": [...]}` 래핑을 유지하고 `pageInfo`를 추가한다.

```json
{
  "posts": [
    {
      "postId": 1,
      "title": "게시글 제목",
      "nickname": "작성자 닉네임",
      "likeCount": 4,
      "createdAt": "2026-07-10T21:37:05"
    }
  ],
  "pageInfo": {
    "page": 0,
    "size": 10,
    "totalCount": 42,
    "totalPages": 5,
    "hasNext": true
  }
}
```

- 페이지 번호 UI에 `totalPages`가 필요해서 전체 개수를 넣는다. 대가로 매 요청마다 count 쿼리가 하나 추가된다(`Page` 반환 시 Spring Data가 자동 실행). count가 부담스러워지면 `Slice`(hasNext만, count 쿼리 없음)로 내리면 되는데, 그러면 페이지 번호 UI는 포기해야 한다.
- `Page` 객체를 그대로 직렬화해서 내보내지 않는다. Spring 내부 타입 구조가 API 명세에 새는 것이고, 버전에 따라 직렬화 형태가 바뀐 적도 있다.
- `hasNext`는 `totalPages`로 계산할 수 있지만, 클라이언트가 다음 버튼 활성화를 바로 판단할 수 있게 명시적으로 내려준다.
- 범위 밖 페이지 요청(전체 5페이지인데 `page=99`)은 오류가 아니라 빈 `posts` + 정상 `pageInfo`를 200으로 준다. "결과 없으면 빈 목록 200" 정책과 같은 맥락.

## 4. 정렬에 보조 키를 붙인다

`createdAt DESC, id DESC`.

정렬 기준 자체는 기존(최신순) 그대로인데, `createdAt`은 유니크하지 않다. 같은 시각에 생성된 글이 있으면 DB가 순서를 보장하지 않고, 정렬이 불안정하면 페이지 경계에서 같은 글이 두 번 나오거나 빠질 수 있다. `id`를 보조 정렬 키로 붙여 순서를 결정적으로 만든다.

## 5. 기존 동작이 바뀐다

파라미터 없이 `GET /posts`를 호출하면 전체가 아니라 첫 페이지(page=0, size=10)가 나온다. "파라미터 없으면 전체 반환"을 남겨두는 절충도 생각해봤지만, 전체 조회를 막겠다고 페이지네이션을 붙여놓고 뒷문을 열어두는 셈이라 두지 않는다.

`posts` 배열 구조는 그대로고 `pageInfo`만 추가라, 기존 필드만 읽는 클라이언트는 깨지지 않는다. api-spec.md의 `GET /posts` 명세는 이 문서 기준으로 갱신해야 한다.

## 6. 필터·검색과의 조합

`author=me`, `category`/`keyword`(설계안)는 모두 같은 엔드포인트의 쿼리 파라미터고, 페이지네이션은 필터·검색이 적용된 결과 집합 위에서 동작한다.

- `GET /posts?author=me&page=1&size=10` — 내 게시글의 두 번째 페이지.
- `totalCount`도 필터 적용 후 개수다. 전체 게시글 수가 아니라 "내 게시글 수".
- 다음에 설계할 내 게시글 조회는 이 규약 위에 필터 조건만 얹는 구조가 된다.

## 7. 구현 방침

- Repository는 `Pageable`을 받아 `Page<Post>`를 반환한다. 정렬은 메서드 이름에 넣지 않고 `PageRequest.of(page, size, Sort.by(...))`로 넘긴다. 보조 정렬 키까지 메서드 이름에 넣으면 이름이 감당이 안 된다.
- 파라미터 보정과 `PageRequest` 생성은 서비스에서 하고, `Page`의 내용(`getContent()`, `getTotalElements()`, `getTotalPages()`, `hasNext()`)을 응답 DTO로 옮긴다. `Page`가 서비스 밖으로 나가지 않는다.
- `@EntityGraph(attributePaths = "user")`는 유지한다. `user`는 `@ManyToOne`이라 페이징과 같이 써도 안전하다. 컬렉션(`@OneToMany`)을 fetch join 하면서 페이징하면 Hibernate가 전체를 메모리에 올려서 페이징하는 함정이 있으니, 나중에 확장할 때 주의.

## 8. 고민할 것들 — 위 결정들의 배경 원리

구현하며 겪는 함정들이 대부분 CS 기초에서 나오는 필연이라, 나중에 다시 봐도 이유를 추적할 수 있게 원리를 남겨둔다.

### OFFSET이 느린 이유 — B+ tree에는 순번이 없다

인덱스는 특정 **키 값**을 O(log n)에 찾지만, `OFFSET 100000`은 "정렬 순서상 100,001번째 행"을 달라는 요청이다. B+ tree 노드는 서브트리의 행 개수를 저장하지 않으므로 DB는 순번을 계산할 수 없고, 리프를 순회하며 10만 건을 읽고 버린다. offset 페이지네이션이 O(offset + size)인 건 자료구조에서 나오는 필연이다. cursor가 빠른 이유도 같은 논리 — 순번이 아니라 키 값으로 시작점을 지정하니 트리 탐색으로 바로 진입한다.

### count 쿼리가 공짜가 아닌 이유 — MVCC

"전체 개수를 어딘가 적어두면 되지 않나" 싶지만, MVCC에서는 트랜잭션마다 보이는 행이 달라서 "지금 행이 몇 개인가"의 단일한 정답이 없다. `COUNT(*)`는 매번 자기 스냅샷에서 보이는 행을 실제로 세야 하고, `deleted_at IS NULL` 조건까지 있으면 조건에 맞는 행을 전부 훑는다. 3절에서 감수하기로 한 count 비용의 정체.

### tie-breaker가 필수인 이유 — 전순서(total order)

`createdAt DESC`만으로는 같은 시각인 행들 사이 순서가 정의되지 않은 부분 순서다. 미정의 구간에서 DB는 실행 계획에 따라 그때그때 다른 순서를 반환할 수 있고, 페이지 1과 2는 별개 쿼리라 두 실행 사이에 순서가 뒤집히면 경계의 행이 중복되거나 빠진다. `id`를 붙이는 건 비교 기준을 전순서로 만들어 결과를 결정적으로 만드는 작업이다(4절).

### 페이지 사이의 중복·누락 — 요청 간에는 격리가 없다

한 트랜잭션 안에서는 스냅샷 격리가 일관된 뷰를 보장하지만, 페이지 요청은 각각 독립된 트랜잭션이다. 요청 사이에 INSERT가 끼어들면 다음 페이지의 offset 기준점이 밀린다 — 컬렉션을 순회하는 도중 다른 스레드가 요소를 삽입하는 상황과 구조가 같다. 트랜잭션을 요청 너머로 유지할 수 없으니 offset 방식에서는 근본적으로 못 막고, 1절에서 감수하기로 한 게 이것이다. cursor가 이 문제에서 자유로운 건 상대 위치(순번)가 아니라 절대 위치(키 값)를 기준점으로 쓰기 때문.

### N+1 — 연산량이 아니라 왕복(RTT)의 문제

`@EntityGraph`를 빼면 목록 10건에 쿼리가 1 + 10개 나간다. 진짜 비용은 DB의 연산량이 아니라 네트워크 왕복 횟수다. 쿼리 하나가 1ms여도 왕복 11번이면 지연이 11배로 쌓인다. 페이지네이션이 size로 N의 상한을 걸어주긴 하지만, 요청당 쿼리 수는 O(1)이어야 정상이다.

### 컬렉션 fetch join + 페이징 — 조인은 행을 곱한다

1:N 조인은 행 수를 곱한다. 게시글 1건에 댓글 5개면 조인 결과는 5행이고, SQL의 `LIMIT`은 엔티티가 아니라 행 기준이라 `LIMIT 10`이 게시글 10건을 보장하지 못한다. Hibernate가 LIMIT을 SQL에서 빼고 전체를 메모리에서 자르는 건 이 때문이다. 지금 안전한 건 `user`가 `@ManyToOne`이라 행이 늘지 않아서지, `@EntityGraph`라서가 아니다 — 이 구분이 핵심이다.

### 입력 보정 — 오버플로와 신뢰 경계

offset은 내부적으로 `page * size` 곱셈이다. int 상한 근처의 page가 들어오면 오버플로로 음수 offset이 될 수 있다. 2절의 보정(clamp)은 UX 판단이면서, 외부 입력을 신뢰 경계에서 정규화하는 방어적 프로그래밍이기도 하다. size 상한 50도 같은 맥락 — 서버 자원 사용량을 클라이언트가 무제한으로 결정하게 두지 않는다.
