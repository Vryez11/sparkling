# 삭제·댓글 정책 메모

댓글 기능을 설계하면서 정리한 판단 기록. 결정마다 "왜 그렇게 했는지"를 남긴다.

## 1. 댓글을 독립 리소스로 볼 것인가

절충안을 택했다 — **소속은 하위 경로로, 조작은 유일 ID로**.

- 조회/작성은 `GET/POST /posts/{postId}/comments` — 댓글은 게시글 없이 존재할 수 없으므로 URI에 소속을 드러낸다.
- 삭제는 `DELETE /comments/{commentId}` — `commentId`가 전역 유일하므로 게시글을 경유할 필요가 없고, 클라이언트도 목록 응답의 `commentId`만 알면 된다.

## 2. 게시글과 댓글의 삭제 정책

둘 다 **soft delete** (`deleted_at` 타임스탬프, NULL이면 활성).

- 게시글을 삭제해도 댓글 행은 DB에 남는다 (cascade 없음). 대신 댓글 목록 조회가 **게시글 생존을 먼저 확인**하므로, 게시글이 삭제되면 그 댓글들도 함께 접근 불가가 된다. 데이터를 지우지 않고도 정책이 지켜지는 구조.
- 댓글 삭제는 `commentId`만으로 동작하며 게시글 생존 여부를 따지지 않는다 — 삭제 API가 게시글 하위 경로가 아니기도 하고, "내 댓글을 지운다"는 행위에 게시글 상태는 무관하다.
- 댓글 삭제 응답은 게시글 삭제와 같은 형식(`commentId` + `deletedAt`)으로 맞춘다.

## 3. 없는 게시글에 댓글 작성 시 404

**목표는 404 Not Found.** 없는(또는 삭제된) 게시글에는 댓글을 달 수 없고, 서비스에서 게시글 생존 확인이 먼저 실행된다.

다만 현재는 예외 처리 체계(`@RestControllerAdvice` + 커스텀 예외)가 미도입이라 `RuntimeException` → **500**이 나간다. 게시글 조회/수정/삭제도 같은 상태이며, 예외 처리 도입은 별도 작업으로 미룬다 (api-spec.md 상태 코드 표의 404/403 "미구현 (현재 500)"과 동일).

## 4. 본인 댓글만 삭제 가능한가

**가능하다.** 댓글 작성자의 ID와 요청자의 JWT `sub`(userId)를 비교해 다르면 거절한다. 목표 상태 코드는 403 Forbidden이지만, 3번과 같은 이유로 현재는 500이 나간다.

## 5. 댓글 목록 정렬과 응답 구조

- **정렬: 오래된 순(`createdAt` ASC).** 댓글은 대화 흐름이라 먼저 달린 댓글이 위에 온다. 게시글 목록이 최신순(DESC)인 것과 다른 건 의도된 차이 — 게시글은 "새 글 발견", 댓글은 "대화 읽기"가 목적이다.
- **응답 구조: `{"comments": [...]}` 래핑** — 게시글 목록의 `{"posts": [...]}`와 일관된 형태.
- **알려진 비일관:** 게시글 목록은 작성자를 `nickname` 필드로, 댓글은 `authorId`/`author`로 내려준다. 댓글은 api-spec의 설계(작성자 프로필 조회·채팅 상대 특정에 `authorId` 사용)를 따랐다. 게시글 응답에 `authorId`를 추가하고 필드명을 `author`로 통일하는 것은 후속 과제.
